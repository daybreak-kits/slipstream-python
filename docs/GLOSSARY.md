# 术语表（GLOSSARY）

本文件只定义**词义**：一个词在我们的代码、接口与界面里指什么，以及容易被叫混的地方。
机制细节、字段口径、状态机参数不在这里展开，一律以 [ssot.md](./ssot.md) 为准（§3 领域模型、§5 核心机制）。

用法约定：

- 代码标识符（表名、字段名、类型名）写在反引号里，界面文案用「」标出。
- 「易混」一栏记录的是**已经踩过的坑**：同一件事被两个名字说过，或两个概念被当成一个。
- 新增或改名词义时改这里；改行为时改 ssot。两处冲突时以 ssot 为准，并回头修本文件。
- 2026-11-15 做过一次改名与语义翻转（组合二元化、优先级方向翻转、缓存口径三分），见 §9。**旧名字一律作废**，不要在新代码和新文案里复活。

## 1. 寻址与模型

| 术语 | 定义 | 易混 |
|---|---|---|
| 渠道 Channel | 一个上游接入点：地址、多密钥、协议与鉴权、改写规则、备注。表 `channels` | 不等于「供应商」；同一供应商可以建多个渠道（不同 key、不同区域） |
| 渠道标识 Slug | 渠道的全局唯一短标识，如 `nim`，是直连名斜杠前的部分 | 与组合名共用命名空间，不能重名 |
| 渠道模型 Channel Model | 渠道下的一个上游模型，加一个对外可调的 `call_model`。表 `channel_models` | 它不是「模型」这个抽象概念，而是「某渠道 + 某上游模型」这条绑定 |
| 上游模型 Upstream Model | 上游 `/models` 返回的原始名字，是请求真正发给上游的 `model` 字段 | 界面上不单独成列，挂在**调用名**旁的图标 tooltip 里 |
| 调用模型 Call Model | 客户端书写的模型名，默认等于上游模型名，可改写，允许含 `/` | 与「上游模型」可以不同（改写或加前缀分组时） |
| 渠道密钥 Channel Key | 渠道下的一条可用凭据，行存 `channel_keys.key_enc`，带备注与启停 | 一个渠道可以有多条密钥；正式请求按 `sha256(request_id)` 选键，**每次请求都可能换一把**。厂商前缀缓存按账号隔离，所以给一个渠道加第二把密钥会当场把缓存打散——加键前必须先有会话亲和 |
| 主密钥 Primary Key | `channels.api_key_enc` 指向的那一条渠道密钥；删掉它要回填下一条启用的密钥 | 不是「列表里的第一条」：同一毫秒创建的密钥排序随机，主密钥靠**内容**指认而不是靠顺序 |
| 直连名 Direct Name | `渠道标识/调用模型`，只按**第一个** `/` 切分；切出来的 `slug` 找不到时，整串会再按原生 `call_model` 命中一次（覆盖 `nvidia/nemotron-…` 这类原生带斜杠的 id） | `nim/openai/gpt-4o` 是渠道 `nim` + 调用模型 `openai/gpt-4o`，不是三段寻址 |
| 调用名 Call Name | 界面上那一列「客户端该写什么」的名字：直连条目是直连名，组合条目是裸名。取代旧词「调用串」 | 旧词「调用串」在后端曾专指直连名、在前端却表示组合裸名，同一个词两个意思；现已废弃 |
| 模型类型 Model Type | 渠道模型的类别，存 `channel_models.model_type`：`chat / embedding / rerank / image_generation / audio_tts / audio_transcription / video`；只有 `chat` 能接 `/chat/completions`，见 ssot §3.5 | 不是上游给的元数据：上游只给模型名，类型是我们按名字或人工判的；也不要把它和「协议 protocol」混为一谈，协议是渠道怎么说、类型是模型干什么 |
| 类型来源 Model Type Source | 这个类型是怎么来的：`default`（未判定）、`upstream`（发现模型时按名字推断）、`manual`（人工改过），存 `channel_models.model_type_source` | 写入接口的 `auto` 是**指令**不是来源值，别把它落库 |
| 逻辑模型 Logical Model | 客户端写裸名（不含 `/`）时解析到的东西：先手动组合、再自动组合 | 裸名与直连名是两套寻址路径，不要互相 fallback |

## 2. 组合（只有两种：手动 / 自动）

| 术语 | 定义 | 易混 |
|---|---|---|
| 组合 Combo | 条目的一类（`kind = combo`），是「一组可路由目标」的上位概念；组合之间靠 `origin` 区分手动与自动 | 组合**不再**分成第三种 kind；旧的 `kind = group` 已取消 |
| 手动组合 Manual Combo | `origin = manual`。落库的组合，成员是渠道模型或子组合，最多 3 层，有自己的 failover 规则与轮数，可编辑可删除 | 旧名「显式组合」作废。它才是「我能改的那个组合」 |
| 自动组合 Auto Combo | `origin = auto`。查询期由各渠道**启用的**、同名且不含 `/` 的 `call_model` 实时聚合出来的组合；不落库、不可编辑、只读 | 旧名「隐式分组」「隐式组合」作废。它没有成员表，所以也没有自己的 priority：成员优先级只能取渠道的 `channels.priority` |
| 自动组合的覆盖范围 | 允许只有一个成员，也允许成员同渠道；不要求「跨渠道」 | 单成员自动组合是故意保留的：客户端可以先写裸名，等渠道扩容时自动获得分流能力，不用改名 |
| 子组合 Child Combo | 作为另一个**手动组合**成员的组合。嵌套深度上限 3 层 | 组合不能引用自己或自己的后代；自动组合不能做别人的成员（它没有落库身份） |
| 成员 Member | 手动组合里的一条目标：一个渠道模型或一个子组合，带自己的 priority 与启停 | 自动组合没有「成员」这个概念，只有派生出来的渠道模型集合 |
| 候选 Candidate | 一次请求在解析后真正可能被调用的渠道模型列表 | 候选是运行时算出来的，成员是配置；封禁与冷却中的成员不进候选 |

## 3. 优先级与故障转移（最容易被叫混的一组）

| 术语 | 定义 | 易混 |
|---|---|---|
| 优先级 priority | 成员的整数排序值，**越大越先调用**（2026-11-15 翻转，此前是越小越先）。`combo_targets.priority` 默认值 1，所以 1 现在表示**最低**优先级 | 优先级**不是序号**：序号是「第几个」的展示位，优先级是「同一层还是不同层」的路由语义。界面上的 `P{n}` 是**优先级层号**（值就是 priority 本身），不是排名，两者不能互相代替 |
| 优先级从哪来 | 手动组合的成员**永远**取 `combo_targets.priority`——编辑器在添加成员时必给它一个值，所以不存在「成员没有优先级」的情况；自动组合没有成员表，成员优先级只能取所属渠道的 `channels.priority` | 不要再写「成员没有优先级时回退到渠道优先级」：那句话只对自动组合成立，对手动组合永远是错的 |
| 同层 / 优先级层 Priority Layer | priority 值相同的成员构成的一层 | 同层内部**等概率随机**，不保序；想固定顺序就必须用不同的 priority |
| 故障转移 Failover | 当前候选失败后按优先级继续尝试下一个 | 只在「不同 priority」之间有先后；同层之间是负载均衡，不是备胎关系 |
| 同层负载均衡 | priority 相同时请求在成员间随机分配，某个成员熔断后自动由同层其他成员承接 | 用户对「优先级」的第一直觉常是「同层=并列备选」，代码语义是「同层=随机分流」。**同层混装不同厂商会打散上游前缀缓存**（各家缓存不互通），见「会话亲和」 |
| 轮次 Round | 顶层手动组合把所有可用成员各试一遍算一轮，可配轮数与兜底动作 | **轮次不是尝试**：一轮之内每个候选各算一次「尝试」，`attempts_json` 的每条都带 `round_index`。旧词把两者都叫 Attempt，已拆开 |
| 会话亲和 Channel Affinity | 同一会话在 TTL（默认 3600s）内**钉住**上次成功服务的渠道模型；钉住可**跨优先级层**（缓存前缀绑渠道/账号，会话连续性优先于层序），被钉成员不可用（封禁 / 冷却 / 排期窗口）时回落层序；失败即清记忆（带 model_id 守卫），流式只在终止标记 200 时写回。键取请求头 `x-session-id`，缺失回退 `x-bili-plugin-conversation`，再缺失不做亲和 | 亲和**跨优先级层生效**（原「只在同一优先级层内」已被 ADR-068 决策 3 推翻）；配置变更（组合/渠道/渠道模型的增删改与优先级调整）bump epoch 使老记忆立即失效；多 key 渠道按会话键稳定哈希选 key，同一会话恒用同一把账号 |

## 4. 可用性与状态

| 术语 | 定义 | 易混 |
|---|---|---|
| 可见状态 Visible Status | 启停轴 × 健康轴合成后给用户看的那一个状态：`normal / half_open / open / fault / disabled`（共五态） | 界面上翻成：正常 / 半开 / 冷却〔熔断〕/ 冷却〔故障〕/ 封禁或冷却〔人工，看 `banned_until` 有没有值〕；后端字段是 `visible_status`，别自己再推一套 |
| 健康状态 Health Status | 只看上游表现的内部状态：`normal / open / half_open / fault` | 面板先看可见状态；只有排查时才拆到健康状态 |
| 派生状态 Derived Status | 由渠道、模型、成员的启用与健康状态**实时推导**出来的可用性，不落任何存储字段 | 目录页的「状态」列读的就是它；它是算出来的，所以不要指望能 PATCH 它，也不要把它和 `model_type_source` 这类「来源标记」混为一谈 |
| **措施只有两种：封禁 / 冷却** | 用户可见文案里，一切「不接流量」的措施只归这两类（2026-11-15 用户裁定，ADR-070）。内部状态位仍是 `enabled` + `banned_until`：`banned_until` 为空 = 封禁，非空 = 冷却到该时刻 | 不要再并列「停用 / 定时封禁 / 熔断 / 故障」四个词——它们全是「封禁」或「冷却」的某一档；判据只看 `banned_until` 有没有值，不需要新字段 |
| 封禁 Ban | 人工设置的**永久**不可用（`enabled=false` 且 `banned_until` 为空），只能人工解除。封禁条目**不出现**在 `/v1/models`，直连调用 404 | 封禁与健康无关；「启用」＝解封并复位熔断器（清计数与冷却/故障计时）。旧词「停用」「定时封禁（永久那档）」统一说「封禁」；代码字段仍叫 `enabled` |
| 冷却 Cooldown | 到期**自动恢复**的不可用，三种来源都算冷却：① 人工设定到期时刻 ② 周期性冷却窗口 ③ 熔断/故障自动触发。冷却期间条目**仍出现在 `/v1/models`**，路由跳过它，直连调用返回 503 + 预计恢复时间 | 旧词「定时封禁」已废弃：选时间 = 冷却，选永久 = 封禁。字段 `banned_until` 是历史名，语义就是「人工冷却的到期时刻」；界面上的「预计 18:05 可用」取它或 `cooldown_until`（自动冷却） |
| 熔断 Breaker Open | 连续失败后短期跳过该模型，是**冷却的自动触发源之一** | 熔断不是独立于冷却的第四种措施，界面上归到「冷却」档；它自己的字段是 `cooldown_until` |
| 故障 Fault | 反复熔断后升级成的较长冷却窗口，到点自动恢复，可带原因 | 故障同样是**冷却**（自动触发、窗口更长）；与封禁的区别是触发者：故障由失败自动升级，封禁由人工 |
| 半开 Half-Open | 冷却结束后只放一个请求试探，成功则恢复、失败则重新熔断 | 界面上单列一态「半开 · 等待下次调用」，比「可用」重、比「冷却」轻 |
| 冷却窗口 Schedule | 周期性复发的冷却区间：每天 / 每周指定星期 / 每月指定日期 + 起止时刻，支持跨天（22:00–02:00，归起始日）。**2026-11-18 用户裁定：界面用词由「计划窗口」改为「冷却窗口」**；机制名（`schedule_json`、排期规则）不变 | 冷却窗口属于冷却（到期自动恢复），不是第三种措施；只对上游模型有意义，**组合不做定时**（ADR-070）；与一次性冷却的区别是复发 |
| 在飞上限 / 准入控制 Admission Control | 网关节点级的过载保护：只统计正在处理中的 `/v1/*` 请求（流式+非流式），达到节点级最大在飞数即对新请求快速失败——429 + `Retry-After`——而不是任由吞吐塌陷；默认 256，`0` = 关闭（ADR-076 决策 5、ADR-077 决策 7） | 不是上游条目的「封禁 / 冷却」：那些决定某个条目接不接流量，准入控制决定网关此刻接不接新请求 |

## 5. 请求、日志与指标

本节时间指标的**基线** = 网关收到请求、进入处理函数的那一刻；所有「到达」均指到达网关侧。**不设 `upstream_sent_ms`**：网关自身开销与上游耗时在指标里合并、不拆分（2026-11-15 用户裁定）。统计维度的归并口径见 §5.2。

| 术语 | 定义 | 易混 |
|---|---|---|
| 使用日志 Request Log | 每次调用落一行，含令牌、耗时、状态、来源。表 `request_logs` | 「日志」永远指使用日志，不是进程日志 |
| 日志来源 source | `chat`（客户端调用）或 `probe`（探测/连接测试）。探测也入账，但令牌为 0、计时为空 | 看请求量与错误率时要按 source 过滤，否则探测会稀释 chat 的数字 |
| 首字时间 TTFT | 上游第一个**可识别增量**（非空 `content` / `reasoning` / `tool_calls` 任一）到达网关的时刻 − 基线 | 不是 TCP 首字节：空帧、SSE 注释不算；是「有东西回来」，不保证有正文（纯推理也算首字） |
| 首答时间 TTFA | 第一段**正文或工具调用**到达的时间（首个 answer surface delta：非空 `content`，或 `tool_calls`/legacy `function_call`） | 工具调用算首答：纯工具调用流 TTFA == TTFT（不再出现「首字有、首答空」）。只有 reasoning、既无正文也无工具调用的流 TTFA 才为空——这是口径，不是丢数据 |
| 尾字时间 TTLT | 上游最后一个增量到达网关的时刻 − 基线；中断流取最后到达的那个增量，`finish_reason` 不另计时 | 与总耗时 `total_ms` 不同：总耗时 = 最后一帧**写给客户端之后**（含回写时间，客户端慢读会拉长），TTLT 不含回写 |
| 缓存词元 Cached Tokens | 上游报告的、被前缀缓存命中的 prompt 部分；我们按 `prompt_tokens_details.cached_tokens` → `usage.cached_tokens` → `usage.prompt_cache_hit_tokens` 三级回退读取 | 上游不上报时为空，不要当 0 参与平均 |
| 缓存命中率 Cache Hit Rate（口径 A） | `cached ÷ prompt`，按 token 加权，是面板上的主指标 | 不是「命中次数 ÷ 请求次数」，也不是各请求比率的算术平均 |
| 请求级命中率 Request Hit Rate（口径 B） | `cached_tokens > 0` 的请求数 ÷ 计入的请求数 | 这是 new-api 一类面板显示的那个数，天然比口径 A 高；两者不可互相替代，也不可拿 A 去比别人的 B |
| 可缓存占比 Cacheable Share（口径 C） | 本请求的 prompt 里，已经在同一会话更早请求中出现过的 token 占比（用 `x-session-id` + prompt 序列估算） | 它回答「本来能命中多少」，与 A 的差就是「该命中却没命中」的部分；没有会话头时算不出来，要显示为「—」而不是 0 |
| 节省 Saved | `Σcached_tokens` 绝对值，及按该模型价格估算的金额 | 它是绝对收益，不随分母变化；汇报「缓存优化成效」时用它，不要只用百分比 |
| 估算用量 usage_estimated | 上游没回报 usage、由我们推断出来的用量 | 中断的流按用户裁定计入：**输入按发出侧已知数算、缓存记 0；输出含已转发的思考块**（ADR-075，`content_chars + reasoning_chars` 折算）。只有 prompt 本身是靠分词器猜出来的行才排除在缓存口径之外 |
| 吞吐 Throughput (t/s) | `completion_tokens ÷ (总耗时 − 首字时间)`，只对流式计算 | 生成窗口 < 100ms 视为无吞吐（上游整段缓冲一次吐出，速率是假的——日志页显「—」是口径，不是丢数据）；非流式一律为空 |
| 网关增量延迟 Gateway Overhead | 同一请求「经网关」与「直连同一上游」的耗时差，用开环（固定到达率）在容量 30%/70%/90% 下测 | 闭环压测里的 p50/p99 是排队时间（利特尔定律），不是网关开销；两者不可混用 |

### 5.1 日志页的三种视图（2026-11-15 新增）

| 术语 | 定义 | 易混 |
|---|---|---|
| 请求 Request | 一次客户端 HTTP 调用，落 `request_logs` 一行 | 与「尝试」不是同一层：一次请求可以有多条尝试 |
| 尝试 Attempt | `attempts_json` 里的一条：一个候选被真正调用（或因为熔断/冷却被跳过）的记录，带 `status`（`success`/`error`/`skipped`）、`ms`、`round_index`、渠道与上游模型 | 失败尝试**有**耗时（`ms` 是真实调用耗时）；`skipped` 才是真的没发出请求、没有耗时。界面不能把两者都留空 |
| 日志视图 Log View | 列表「一行代表什么」的选择，三个取值：逐次请求（默认）/ 按组合聚合 / 按状态聚合 | 它是展示层概念，不改变能搜到什么 |
| 事实层 / 展示层 | 事实层 = 请求 + 尝试，筛选与搜索只作用在这里；展示层 = 一行怎么拼。搜索永远先过滤事实、再按当前视图聚合（filter-then-aggregate） | 一旦让聚合先发生、再在聚合行上搜索，被聚合掉的成员就永远搜不到——这是 2026-11-15 修过的 bug |
| 状态段 Status Segment | 按状态聚合视图的一行：同一**上游模型**上**连续相同状态码**的尝试序列；上游模型变化、状态码变化、或与下一条尝试间隔超过空闲阈值即断段 | 不是「按状态码分组统计」——同一段里时间必须连续，中间夹一次 200 就会切段 |
| 思考块 Thinking Block | 上游返回的推理内容（`reasoning_content` / `reasoning`），在模型试验里按可折叠块展示；没有就显式标「无思考块」 | 它不是回答正文，不计入可见正文的 TTFA 口径 |

### 5.2 统计维度与展示名（按实体 id 归并，2026-11-15）

| 术语 | 定义 | 易混 |
|---|---|---|
| 维度身份 Dimension Identity | 看板 / 日志的统计维度按**实体 id** 归并，不按名字：同一实体改名前后仍是同一个维度 | 名字只是展示层，不是身份；改名不会把统计劈成两半 |
| 上游渠道维度 | `channel_id`。日志行只存 `final_channel_model_id`，经 `channel_models.channel_id` 回推出渠道 | 展示名取渠道**当前** slug / name；日志行的 `channel_name` 只是当时快照 |
| 上游模型维度 | `final_channel_model_id`（「某渠道 + 某上游模型」这条绑定本身） | 上游改了显示名但 id 不变 → 仍归并成一行 |
| 综合模型维度 | `resolved_combo_id`；回退链：组合命中 → `resolved_combo_id`，直连 → `final_channel_model_id`，自动组合 → 折叠名 | 自动组合没有落库身份，只能按折叠名归并，改名会短暂分裂 |
| 展示名与历史快照 | 展示一律取实体**当前名**；历史写法只留在日志行快照字段（`channel_name` / `upstream_model` / `requested_model`）供审计 | 排查旧日志以快照为准，统计聚合以 id 为准 |
| 名字回退 Fallback | 拿不到 id 的历史行按名字折叠回退 | 只为兼容旧数据；新行都有 id，不再走名字回退 |

## 6. 探测与测试

| 术语 | 定义 | 易混 |
|---|---|---|
| 探测 Probe | 对某个**渠道模型**发一次最小请求，验证它能不能答；状态 `ok / timeout / error / unknown` | 探测结果只是健康信号，不改配置 |
| 连接测试 Connection Test | 对**渠道**发一次最小请求，验证地址与凭据是否通 | 与探测测的对象不同：一个测渠道可达性，一个测模型可答性 |
| 模型连接探测 | 对该模型发真实聊天并校验正文；成功会写回健康状态、清空冷却（API 值 `mode=deep`） | 只有它能把熔断触发的冷却恢复成可用，模型拉取探测与连接测试不能 |
| 模型拉取探测 | 只查模型列表/可达性，不发完整聊天（API 值 `mode=shallow`） | 不改变健康状态，常用来刷新「这个模型还在不在」 |
| 未知 unknown | 从未探测过 | 不随时间自动过期，展示时必须带探测时间，否则会被误读成「现在不可用」 |

## 7. 「条目」与配置对象

| 术语 | 定义 | 易混 |
|---|---|---|
| 条目 Entry | 目录接口 `/api/catalog` 返回的一行：`kind = direct`（直连）或 `kind = combo`（组合，带 `origin = manual | auto`） | 早期叫过「模型列表」，容易让人以为只有直连 |
| 条目 kind | 只有两个取值：`direct` / `combo`。旧值 `group` 已取消 | 徽标文案与 kind 不再一一对应，因为 combo 还要靠 origin 细分：界面上是「直连 / 手动组合 / 自动组合」三种文案对两个 kind |
| 组合来源 origin | `manual`（手动组合，落库可编辑）或 `auto`（自动组合，派生只读） | 它不是 kind 的第三、第四种取值；直连条目没有 origin |
| 状态列 Status Cell | 目录页「状态」格里显示的东西：可见状态 + 预计恢复时间 + 一句 `status_message`，由 `/api/catalog` 现成给出，前端不自己再推 | 它不是健康状态；五态（正常 / 半开 / 冷却〔熔断〕/ 冷却〔故障〕/ 封禁或冷却〔人工〕）按 fault>open>half_open>disabled>normal 取最差；日常只看这一列，排查才拆到 `health_status` |
| 状态摘要 status_message | 聚合出来的一句人话，如「3 个成员中 1 个冷却中（熔断）」「2 个成员中 1 个冷却中（故障）」 | 它是给人看的解释，不是机器判定依据；判定一律看 `visible_status` 与时间字段 |
| 模型管理 Models page | `/catalog` **一页**（2026-11-15 起取消「组合模型」页签）：页头有「新建组合」；直连行有复制、加入组合、启用 / 封禁（永久）/ 冷却（定时）；手动组合行有编辑、删除；自动组合行无操作且标「只读 · 实时派生」 | 旧书签 `/combos` 仍能打开，自动落到这一页并定位到组合 |
| 度量条 Metric Strip | 日志页顶部那排数字卡：用量/开销/RPM/TPM/缓存命中率，每项带一句 hint 说明分母或样本 | 它是当前筛选下的汇总，与下方列表同步变化，不是全库总量 |
| 平均 P95 Average P95 | 看板 P95 趋势的合计：各模型 p95 按请求数加权平均 | 不是把所有请求混在一起重算 P95，分布偏斜时两者会不同 |

## 8. 传输与切流

| 术语 | 定义 | 易混 |
|---|---|---|
| 传输臂 Transport arm | 同一条上游调用的两种实现之一：`httpx` 臂（原生收发送字节，现为默认）与 `litellm` 臂（走 LiteLLM SDK，只能整实例开启：`UPSTREAM_TRANSPORT` 是全局配置，没有渠道级覆盖）。臂是「实现」，不是渠道属性 | 不等于「传输协议」；两条臂打的是同一个上游端点。也不等于「回退」——回退是失败后的动作，臂是配置 |
| 切流窗口 Cutover window | 把一个默认值或一条路径换到另一侧之后，用来确认没坏的那段观察期：按 24 小时算，盯 5xx 率、P95 首字、P95 总耗时、CPU/请求四个指标，任一恶化 >20% 且持续 15 分钟即回滚 | 不是「安静窗口」——不要求两次测量都不受干扰；判据是方向在同工况两次测量里一致 + 回滚成本只有一条 env |
| 头透传 Header Passthrough | 网关对「头」的默认处理语义：出站以客户端请求头为基线，剥传输层头与客户端凭据后叠加网关自己的头，再交给渠道规则；入站上游响应头原样转发，网关必需头最后覆盖。机制见 ssot §5.6、ADR-074 | 不是「全量转发」：凭据、hop-by-hop、`host/content-length` 永远不过网关；`content-type` 出站由网关按协议固定，渠道规则同样改不动它 |
| 客户端凭据 Client Credentials | 客户端带进来的身份凭据：`authorization / proxy-authorization / cookie / api-key / x-api-key`。**一律不进上游**，上游只认渠道密钥（ADR-074 决策 2） | 与「用户密钥」不是一回事：用户密钥只用于网关鉴权，渠道密钥只用于上游鉴权；两个都不能沿另一条路透传 |
| 传输层头 Hop-by-hop Headers | 只描述当前这一跳连接的头（`connection / keep-alive / te / trailer / transfer-encoding / upgrade / proxy-*`），两端都不转发（ADR-074 决策 1） | 与端到端头（`content-type`、`x-request-id`）相对；判据是「换一跳是否还成立」 |
| 网关必需头 Gateway-owned Headers | 由网关最后写入、不允许上游或渠道规则覆盖的头：流式的 `content-type: text/event-stream`、`cache-control: no-cache`、`x-accel-buffering: no`，以及 `x-request-id`（ADR-074 决策 5）；出站侧的 `content-type` / `content-length` / `host` / `x-request-id` 同样对渠道规则关闭（ADR-074 决策 4，2026-11-15 裁定） | 覆盖发生在合并**之后**且大小写不敏感；上游同名不同大小写的头不会与网关的并存 |
| 流式转发路径 Stream Relay Path | 上游 SSE 到客户端的转发实现，三态：**直通块**（字节原样）、**改写块**（块内逐行跟踪+改写后重组，ADR-078）、**逐行**（仅测试替身退化）。三态都按网络块产出消息，跟踪（usage 兜底/断流判定/relay 累计）逐帧照跑 | 三态是「实现路径」不是「行为差异」：error 帧不发客户端、[DONE] 合成、首字节后不重试等契约完全一致；不要把「直连名=逐行慢路径」当成现存事实（2026-11-18 ADR-078 后三态同粒度） |

## 9. 改名与翻转记录（2026-11-15，用户裁定）

| 旧 | 新 | 原因 |
|---|---|---|
| 显式组合 | **手动组合**（`origin = manual`） | 「显式/隐式」这一对让人以为它们是同一种东西的两种开关；实际一个是落库记录、一个是实时派生 |
| 隐式分组 / 隐式组合 | **自动组合**（`origin = auto`） | 叫「隐式组合」会让人去找编辑按钮；它只读、不落库、随时可变 |
| `kind = direct / combo / group` | `kind = direct / combo` + `origin = manual / auto` | 组合是一类，手动/自动是它的来源属性，不是第三种条目 |
| 调用串 | **调用名** | 后端曾用它专指直连名，前端却拿它当组合裸名的列名，一詞两义 |
| 优先级「越小越先调用」 | **「越大越先调用」** | 用户按直觉裁定：优先级高的先被调用；数据由用户自行调整，代码只改行为 |
| 缓存命中率（单一数字） | 口径 A/B/C + 节省 | 单数不可比：请求级命中率天然高于 token 加权命中率，且分母混着必然不命中的请求 |

## 10. 路由策略与观察期（ADR-077，2026-11-16）

| 术语 | 定义 | 易混 |
|---|---|---|
| 路由策略 Route Strategy | 同层成员的排序规则：`uniform` 均匀随机（默认）/ `stable` 稳定优先 / `cost` 成本优先 / `latency` 延迟优先 | 只作用于同层内部；跨层顺序永远由优先级绝对控制，策略不能把低优先级成员排到前面 |
| 时间窗口 Sampling Window | 滑动窗口，按尝试的事件时间回看 N 分钟计算成员统计。选项 15/30/60/自定义，最小 15、上限 1440，默认 30 | 是「回看窗」不是「固定窗格」；历史数据滑出窗口即视为无数据 |
| 观察期 Observation | 窗口内成功尝试 < 30 次的成员按负载均衡均等参与（均匀随机槽位），攒足样本后才并入策略排序 | 新加入成员和冷却解除成员都走观察期；窗口内没人够样本时整层回退均匀随机 |
| 成本口径（策略） | 每百万 token 有效均价 = 窗口内 Σ实际计费费用 ÷ Σ(prompt_tokens + completion_tokens) × 1M（费用含缓存读/写按各自单价计的部分，prompt_tokens 含缓存命中）；未配置价格的成员按 0 参与 | 不是单次请求均价比（会因会话大小失真）；也不是单价表比较；缓存命中越多有效均价越低（奖励行为），未配置成员天然排最前。「按 0 参与」是排序语义，不代表成员免费——金额展示口径见「未配置单价」 |
| 未配置单价 Unconfigured Price | 有词元消耗而费用为 0 时，展示层判为单价未配置：数值位显示「—」或「未配置单价」，禁渲染 `$0.00`（会被读成免费） | 与「免费」不同义：计费层 0 与未配置不可区分（ADR-082），系统当前不支持显式标价 0；真实成本为 0 的空请求（无词元）不触发此口径 |
| 观察窗口（路由） | 「时间窗口」与「观察期」的合称：路由策略只在成员有足够窗口数据时生效，统计按时间窗口滑动回看，样本不足的成员按观察期规则均等参与（ADR-077） | 不是 §8 的「切流窗口」（切流后的验收观察期）；具体机制分见「时间窗口」「观察期」两条，不要另造叫法 |

## 12. 基准与负载（2026-11-18）

| 术语 | 定义 | 易混 |
|---|---|---|
| 负载臂 Bench Arm | 同一负载下被测对象的一个配置：`direct`（直连 mock，天花板）/ `slipstream`（裸转发或带改写）/ `agentgateway`（同） | 臂是「被测配置」，不是渠道的传输臂（§8 传输臂）；两词都在用，语境不同 |
| 生产形态臂 Production-shape Arm | 请求体与流长按真实生产比例构造的负载档：输入 50K–300K tok（约 200KB–1.2MB 请求体）、输出 300–20K tok（对应 SSE 帧数） | 不是「生产环境的流量回放」；是合成负载里最接近生产的那一档 |
| 特征臂 Features-on Arm | 开启路由 + 请求头/体改写 + 响应头/体改写的对比腿（用户裁定的必测条件，ADR-076 决策 4 的扩展）；与「裸转发腿」成对出现 | 特征臂≠生产形态臂：前者是功能开关维度，后者是负载大小维度，矩阵里正交 |
| 开环矩阵 Open-loop Matrix | 固定到达率（QPS 64/128/256/512/1024）的压力网格，延迟从应发时刻起算（纠正 coordinated omission）；验收口径（ADR-076） | 不是闭环阶梯（PERFORMANCE_REPORT §2 的旧口径）；两者数字不可互比 |
| 天花板自证 Ceiling Self-certification | 压测前置动作：直连臂先跑满梯度证明「mock + 负载器」不是瓶颈（PERFORMANCE_REPORT §1.3 判据）；不过此关的对比数字一律作废 | 它证明的是「网关数字可信的上界」，不是网关自身的容量 |
| 塌陷 Collapse | 网关在过载下吞吐不升反降、延迟进入秒级的状态；与「准入快速失败（429 shedding）」不同——shedding 是设计行为（ADR-076 决策 5），塌陷是 shedding 前的失稳 | 看到大量 429 不等于塌陷：完成率稳住、延迟可控的 shedding 是过载保护的正常形态 |
