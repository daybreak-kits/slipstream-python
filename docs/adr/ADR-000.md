# ADR 格式、编号与编目规则

---
status: accepted
date: 2026-11-14
---

本文件是 `docs/adr/` 的目录说明与格式约定，本身不是一条决策。

## 命名

`ADR-{三位编号}-{kebab-短标题}.md`，例如 `ADR-057-zero-sql-usage-pipeline.md`。编号连续、不复用；文件被取代时保留原文件并在文首标注 `status: superseded by ADR-NNN`，不删除。

## 文件结构

每条 ADR 固定六段：背景 / 决策 / 理由 / 备选与否决原因 / 后果与影响 / 相关代码与文档。段落可以短，但「备选与否决原因」不能省——只写最终方案而不写为什么不选别的，下一个人会把同样的方案再提一遍。

## 状态词

| 状态 | 含义 |
|---|---|
| `accepted` | 决策已生效，代码与配置与本条一致 |
| `accepted, in progress` | 决策已生效，落地未完成（例：PostgreSQL 分支写好但未对真实服务器执行过） |
| `superseded by ADR-NNN` | 已被后续决策取代，保留原文 |
| `rejected` | 评估后否决，留档防止重提 |

## 可选 front-matter 字段

| 字段 | 取值 | 含义 |
|---|---|---|
| `backfilled` | `true` | 该文件是 2026-11-14 从 `ssot.md` §13 压缩表回填的：决策与后果两栏逐字复制，理由与备选**当时未记录**，文件里不补写没有出处的解释。没有该字段表示是原生撰写的 ADR |
| `supersedes` | `ADR-0NN`，多条用 `,` 分隔 | 本条取代了哪些旧决策。写在新文件上，与旧文件的 `status: superseded by` + `superseded_by` 配对；两边都写才能双向查到 |
| `superseded_by` | `ADR-0NN` | 取代本条的那条决策的编号，与 `status: superseded by ADR-NNN` 同时写：状态词给人读，字段给脚本（`grep '^superseded_by:' docs/adr/*.md` 一次列出全部失效决策）。整体失效才写；部分失效用下面的 `partially_superseded_by` |
| `partially_superseded_by` | `ADR-0NN`，多条用 `,` 分隔 | 主决策仍生效，但其中某一部分已被后来的 ADR 改过：`status` 仍写 `accepted`，被改的是哪一部分写在「后果与影响」里。整体失效不用这个字段，直接 `status: superseded by ADR-0NN` |

## 什么时候写 ADR

三条同时成立才写：① 改回去代价显著；② 读者看到代码会问「为什么是这样」；③ 当时确有其它可选方案。三条缺一就不写——容易反悔的决定直接改，写了也会变成噪音。

## 与其它文档的分工

- `docs/ssot.md`：**机制与口径**的事实源（现在是什么、怎么算、配置在哪）。
- `docs/adr/`：**决策与理由**（为什么是这样、否决了什么、后果是什么）。
- `docs/INDEX.md`：按界面导航（每个页面 → 接口 / ADR / ssot 章节 / 测试）。
- `docs/GLOSSARY.md`：词义，不含机制。
- `docs/PERFORMANCE_REPORT.md` 与 `docs/testing.md`：实测证据与复现命令，不是事实源。

新决策一律「建文件 + 在 `ssot.md` §13 加一行」两处同步；只加行不建文件只适用于一次性的小选择。
