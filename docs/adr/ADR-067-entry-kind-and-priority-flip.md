## 背景

`/api/catalog` 的每一行原本有三种 `kind`：`direct`、`combo`、`group`。三者在实现上是两条完全不同的路径——combo 是落库记录（`combos`/`combo_targets`，最多 3 层、带 failover 与轮数），group 是查询期由同名 `call_model` 实时聚合出来的派生集合（不落库、只读、不可编辑）——但它们对客户端暴露的语义是同一个：写一个不含 `/` 的名字就能路由过去。于是文档里长期并存三种叫法（显式组合/隐式分组/隐式组合）、两种徽标文案，以及一句只对一半情况成立的规则：「成员没有优先级时取渠道优先级」。

词表与实现的冲突在这一轮被逐条点出（GLOSSARY §9 记录了改写前的原文），根因是同一个：**把「组合」和「它从哪来」压进了同一个字段**。`kind` 同时承担「这是不是组合」和「这个组合是手动配的还是自动算的」两件事，于是每加一种组合来源 `kind` 就要多一个取值，而所有 `kind === 'combo'` 的判断都会静默漏掉新来源。

同时，优先级的方向与用户直觉相反，而 UI 一直用 `P{n}` 展示：`P1` 排在最前面、却代表最低优先级。用户提出「优先级越高越先被调用」，并说明手动组合的成员在添加时必然被赋值（编辑器强制），所以「无优先级」这个状态只可能出现在自动组合上。

## 决策

1. **`kind` 只留两个取值：`direct` | `combo`；组合的来源移到 `origin`：`manual` | `auto`。** 旧 `kind = group` 取消，`/api/catalog` 对所有组合行返回 `kind: "combo"` + `origin`。理由：组合是一类，手动/自动是它的属性；「这是不是组合」只看 `kind`，「能不能编辑」只看 `origin`，两个问题不再互相污染。界面三种文案：直连 / 手动组合 / 自动组合（`origin=auto` 另标「只读 · 实时派生」）。
2. **优先级数值越大越先调用。** 排序从 `priority ASC` 改为 `priority DESC`，同值仍在同一层内等概率随机（`order_candidates`，api/src/l05_service/routing.py:489-503）。理由：用户按直觉裁定；翻转只改比较方向，不触碰分层结构与随机逻辑，零数据迁移。
3. **优先级来源二元化，两个来源都恒有值。** 手动组合的成员永远取 `combo_targets.priority`（编辑器添加成员时必赋，默认 1）；自动组合没有成员表，成员取 `channels.priority`。**删除**「成员没有优先级时回退到渠道优先级」这条规则。理由：用户明确手动组合不存在无优先级状态；保留回退等于给手动组合留一条永远走不到的岔路，而它曾被写成跨两种组合的通用规则，正是文档与实现分叉的起点。
4. **`P{n}` 是优先级层号，不是序号。** 徽标数字就是 `priority` 本身，列表按 `priority DESC` 渲染（因此 `P40` 在 `P1` 之前）。理由：把层号当序号渲染，翻转后会出现「序号倒着数」；隐藏真实值又会让用户无法对照配置。
5. **数据不迁移。** 现有 `combo_targets.priority` 与 `channels.priority` 原样保留，语义随方向翻转；由用户自行调整数值。理由：用户明确「现有的组合数据不用你改，我自己调」；自动迁移会把「1 表示最低」静默换成「1 表示最高」，而旧数据的意图只有用户知道。

## 后果

- 旧书签 `/combos` 保留重定向到模型管理页；「组合模型」页签删除，直连与组合同页呈现，页头「新建组合」。
- 任何 `kind === 'group'` 的残留判断都会失效。这类判断在巡检中按错误处理，不留兼容分支。
- `P{n}` 的视觉顺序变了：同一份配置翻转后，首行从 `P1` 变成数值最大的那一层。一次性阅读冲击，接受。
- 测试面：api 侧 20 个、web 侧 20 个文件出现 `priority` 字样（`api/tests/test_combos.py`、`test_rounds.py`、`test_implicit_groups.py`、`test_catalog.py`、`web/src/lib/combos.ts`、`web/src/pages/combos.tsx`、`web/src/components/combos/combo-editor-dialog.tsx` 等）。凡断言顺序的一律按新方向重写；顺序断言必须显式写「按 priority 降序」，不得依赖插入序。
- 定时封禁（`banned_until`）作为状态轴的一部分同批落地：到期靠读取时惰性判活，不引入定时器。

## 新成员默认优先级（实施期补充决定）

原编辑器给新成员赋「当前最大值 + 1」，在旧方向下含义是「排在最后」。翻转后同样的算式会变成「插队到最前、抢走全部流量」，必须同步改。当时给出三个选项并询问用户，未在等待窗口内得到回复，因此按**最小改写**落定：

- **新成员取当前成员里的最小值**（无成员时取 1），即并入最低优先级层、与该层成员同层随机分流。
- 否掉「最小值 − 1」：`priority` 在接口层有 `ge=1, le=1000` 校验，全 P1 的组合加成员会算出 0 而非法。
- 否掉「全员 +1 再取 1」：会静默改写用户手调过的每一个数字，且顶到 1000 时无法执行。

该规则收敛在 `web/src/lib/combos-editor.ts` 的 `nextMemberPriority(members)` 一处，用户若要换成「新成员独占最后一层」，改这一行即可。
