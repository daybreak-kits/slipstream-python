## 背景

面板上的「缓存命中率」是一个数：`Σcached_tokens / Σprompt_tokens`，24h 读数 77.10%，今日窗口 69.19%。用户拿它跟 new-api 的 95%+ 对比，判断我们少了缓存优化。查证两侧口径后：

- 2026-11-15 复核推翻了上一版结论：**new-api 侧不是请求级口径**。用户按 `usage 缓存词元 ÷ 输入词元` 实测 new-api 得到 **90%+**，与我们同为 token 加权；上一版据界面文案推断的「请求级」判定不适用于用户比较的那个数字，差异**不是**记账口径造成的。
- 我们面板的主指标是 token 加权，分母含所有 prompt token，包括必然不命中的首轮、新增内容，以及**同一会话里换了渠道成员的轮次**。真实差距在行为，不在算法：见下方「复核」。

更关键的是库里能查到缺口在哪。24h 未命中 135,931,703 token，其中 **88.77%（90,315,161）不是新内容**——同一会话的上一条请求里已经出现过，只是这次没命中；真正新增内容仅 11.23%。若这 90M 全命中，24h 读数是 92.31%。

归因（24h，零命中 366 行 / 37,437,179 prompt token）：同渠道同会话间隔 <15 分钟仍整段归零 **61.58%**；换渠道/换模型 **20.24%**；无会话头 15.29%。代码侧对应三个事实：网关从不注入 `cache_control` 或 `prompt_cache_key`；同优先级层内每次尝试都 `random.shuffle`（跨厂商分流，各家缓存不互通）；`select_channel_api_key` 按 `sha256(request_id)` 选键（api/src/l05_service/channels.py:191-203）——今天每渠道只有一把 key 所以 `len(keys)==1` 短路，加第二把 key 就会逐请求换账号，把厂商按账号隔离的缓存整片打散。

## 决策

1. **命中率拆四个口径，主指标仍是 token 加权。** A 缓存命中率 `Σcached/Σprompt`（主）；B 请求级命中率 `cached>0 的请求数 ÷ 计入请求数`（与按请求计的报表可比）；C 可缓存占比（本请求 prompt 中已在同会话更早请求出现过的 token 占比，答「本来能命中多少」）；D 节省 `Σcached_tokens` 及按模型价格估算的金额。卡面一行显示 A，hover 展开四项并标注分母与样本量。理由：单数不可比，且分母混着必然不命中的请求；汇报成效用 D（绝对值不随分母漂移）。
2. **中断的流计入聚合，输入按发出侧已知数、缓存记 0。** 现状是 `usage_estimated` 为真的行整个排除在缓存口径外（api/src/l05_service/aggregates.py:79-86），改为按上游口径入账，只有 prompt 本身靠分词器猜的行才排除。理由：用户确认上游就是「输入照发出去的算、缓存为 0」，排除会让中断多的时段虚高。
3. **加会话亲和，跨层钉住上次成功的成员（2026-11-15 修订）。** 键取 `x-session-id`，回退 `x-bili-plugin-conversation`，再缺失则不做亲和；TTL 3600s；命中时把上次成功的 channel_model 提到队首，**即使它在更低优先级层**；该成员当前不可用（渠道停用、模型封禁、熔断打开）才回落层序；这次调用失败立刻清记忆继续往下走；只有真正拿到终止标记才写回（prime 成功不算）。理由：复核测得同会话换成员时 A 从 78.42% 掉到 64.12%，占 16.0% 的 token——厂商前缀缓存按「凭据 + 上游模型」隔离，粘性是不改请求体就能拿到命中率的唯一手段。**配置变更即失效**：组合/渠道/渠道模型的增删改与优先级调整会 bump 亲和 epoch，老记忆立即作废、下一个请求按新层序选（用户改完配置不必等 TTL）；**多 key 渠道按会话粘性选 key**：有会话键时用 `sha256('session:'+key) % 启用 key 数` 选主 key，同一会话恒用同一把账号（上游前缀缓存按账号隔离，逐请求换 key 等于逐请求换缓存域），无会话键时保持按 `request_id` 选。**原「只在同层内生效」被推翻**：同层内保持等概率随机，但跨层时连续性优先于单次层序，代价是负载倾斜更明显。
4. **不改请求体内容：允许 L0（不改体）与 L1（字节稳定），不做 L2。** 具体地，不注入 `cache_control`、不改 messages 顺序、不重排 system；只保证同一会话的请求字节前缀稳定（`json=` 序列化的键序来自 dict 插入序，语义相同也可能字节不同，属 L1 要盯的点）。理由：注入会改变上游计费与行为，且各家支持面不一（Anthropic 需显式断点、OpenAI 自动、DeepSeek 只认从 token 0 起的完整前缀），逐条审批后再做。
5. **验证方式改为厂商 A/B 回放，不再压 mock。** 用少量真实额度把同一批会话回放到两个配置，比较 A/B/C/D 四项而不是总分。理由：既有 bench2 里 mock 缓存恒为 0、NIM 与 OpenRouter 免费层 `cached_tokens` 恒为 0，缓存结论不可能从那里得出。
6. **多 key 渠道按会话粘性选 key（决策 3 已落地）。** 亲和上线后第二把 key 才安全：有会话键时按会话稳定哈希选主 key，无会话键仍按 `request_id`（行为逐字节不变）。这条写进代码注释与文档，不靠记忆。

## 复核（2026-11-15 10:00 前后 24h 窗口，app.db 6081 条计入请求）

把「90%+ 与 78% 为何并存」拆开（Σprompt 652,700,665 / Σcached 508,935,770，A=77.97%）：

| 切片 | 行数 | token 占比 | 该切片 A |
|---|---|---|---|
| 全部请求（面板主指标） | 6081 | 100% | **77.97%** |
| r>90% 的行 | 3811 | 64.8% | 96.59% |
| r 在 0~50% | 812 | 12.9% | ~30% |
| r=0 | 382 | 6.2% | 0% |
| 同会话重复轮次（cached_b ÷ prompt_b） | 4539 对 | — | 中位 **94.31%** |
| 同会话、**成员没换** | 5996 | 83.7% | **78.42%** |
| 同会话、**成员换了** | 733 | 16.0% | **64.12%** |

结论：

1. **典型重复轮次就在 94%**，与用户实测 new-api 的 90%+ 同量级；78% 是把冷启动、切成员、厂商零命中一起做了 token 加权平均的结果。两个数都对，差的是切片。
2. **头号可修原因是切成员**：同会话换成员时 A 掉到 64.12%，占 16.0% 的 token。厂商前缀缓存按「凭据 + 上游模型」隔离，`basis` 的四个成员分属 VendorQ / minimaxi / SenseNova 且对应不同上游模型（deepseek-flash / deepseek-v4-flash / MiniMax-M3.1-Flash / sensenova-6.8-flash），换成员即换隔离域。**因此把亲和决策从「同层内提权」改成「跨层钉住上次成功的成员」**（决策 3 已同步修订）。
3. **厂商侧零命中 6.2% 只能观测**：378 次「同会话、同成员、间隔几秒、prompt 正常增长（+1,897）」的请求仍 cached=0，92% 落在 VendorQ；与请求改写无关（rewrite_applied=1 的 5054 行 A=78.10%，=0 的 993 行 A=78.07%）。

## 实测（2026-11-15 03:54 前后 24h 窗口，app.db 6029 行）

口径落地后在同一份只读库上量到：**A = 76.98%**（与改造前同值——被排除的 47 行 prompt 全为 0，说明旧口径在本库并未虚高，虚高风险只在「中断多且 prompt 已知」的时段出现）；**B = 93.40%**（5587/5982）；**C = 72.86%**（459,346,044 / 630,411,383，21 个 session）；**D saved_tokens = 485,290,087、saved_usd = 0.00**。

D 为 0 不是公式错：该库 17 个渠道模型里只有 1 个配了 input 价、且 cache_read 价为空，按规则回落成「按 input 价计 → 无节省」。**面板必须在 D 为 0 且价格缺失时说明原因**，否则会被读成「缓存一点没省」。B 与 A 相差约 16pt 是「请求级 vs token 加权」的记账差，但**这不是与 new-api 对不上号的原因**（见「复核」）。

## 后果

- 面板数字会变：中断行入账后，中断多的时段 A 会下降（更贴近上游真实口径）。任何「指标变差」的判断先确认真是行为变差还是口径变了。
- **亲和语义变更的代价**：亲和现在跨层钉住成员，会让高优先级层在有活跃会话时不再被优先使用，负载倾斜比原来的「同层内提权」更明显（会话粘在一个成员上）。这是为缓存前缀连续性付的代价，失败即清记忆并回落层序。
- 亲和会让同层分流不均（会话粘在一个成员上），负载倾斜是可接受代价；失败才换，语义与 new-api 的 `SwitchOnSuccess` 一致。
- 亲和按**进程内 TTL 表**实现（`OrderedDict` + `time.monotonic`，TTL 3600s、容量 4096、装载时清理过期）。因此它只在单进程 uvicorn 下完整有效：**重启丢失、多 worker 各自一份**，扩容后会按 worker 数稀释。要跨进程需换共享存储（Redis 或 DB 表），涉及 `orm.py`/`db.py` 迁移，本轮明确不做，模块注释已写明这条限制。
- 亲和 epoch 是**进程内计数器**：配置变更只清本 worker 的亲和，多 worker 部署下其他 worker 的老记忆仍在（其失效依赖 TTL 或目标不可用）。跨 worker 立即失效需把记忆绑到 DB catalog version，本轮明确不做。
- C 口径在无会话头时算不出来，必须显示「—」而不是 0，否则把「不知道」画成「没命中」。
- 短期拿不到 Anthropic 显式断点的额外命中，这是有意的范围限制（L2 逐条审批）。
