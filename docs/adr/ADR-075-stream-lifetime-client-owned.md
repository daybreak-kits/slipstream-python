## 背景

一次真实故障暴露了两个口径问题。某 ~62K 输入上下文的编码代理会话连续请求 `glm-5.3-flash`：上游每轮只吐思考块（~975KB / 119s），始终不出正文、不给完成标记，被网关的**流式总闸**掐断——`REQUEST_TIMEOUT_S=120` 派生出流观察器的内部 deadline，httpx 层也拿到 `Timeout(total=120)`——每轮都在 120s 整被判定超时，重试 3 次全部同样死法，客户端收到连续 502。使用日志的失败行显示「输入 62475 / 输出 0」：用户质疑，明明收到了大量思考块，为什么输出是 0？

拆开是两个独立的决定：

1. **总闸**：网关在流式转发上强加了全局时长上限。但流式请求的生命周期本来就归客户端管——客户端愿意等多久是客户端的事；网关该看住的是「连接死了」（建连失败、首字节迟迟不来、逐块读空闲），而不是「用了多久」。
2. **估算口径**：上游 usage 只随正常完成到达；流中途死掉时网关退回本地估算，而估算只数正文字符，思考块不计入 → 输出恒为 0。但上游确实生成并（按其计费口径）结算了这些思考 token——OpenAI 兼容语义下 reasoning 计入 completion。

## 决策

1. **流式转发不设总闸。** 删除两条流观察器（`UpstreamStream` / `LiteLLMUpstreamStream`）的 `total_timeout_s` 参数与内部 deadline；流式上游请求的 httpx timeout 改为 `Timeout(None, connect=…, read=…)`（total 缺席，请求 `extensions` 里没有 `timeout` 键）。流的三条生存边界只剩：上游自然发完（finish_reason / `[DONE]`）、客户端断开（既有 cancelled/499 清理路径）、逐块读空闲超时（`UPSTREAM_READ_TIMEOUT_S`——它判「连接死了」，不判「用得久」）。建连超时与首字节超时保留。**非流式请求保留总超时**（一次非流式 HTTP 调用必须有时限），`REQUEST_TIMEOUT_S` 语义收窄为「非流式总超时 + 重试预算参照」，不变量 11（重试预算 ≤ 请求超时）照旧，只对非流式承诺。
2. **失败兜底估算把已转发的思考块计入输出。** 两个观察器各新增无上限计数器 `reasoning_chars`（`reasoning_content` 维持 64K 截断，仅供 request_bodies 快照）；`chat._usage()` 的估算分支改为按 `content_chars + reasoning_chars` 折算。上游 usage 正常到达时仍以 usage 为准，语义不变。

## 明确不做

- 不给「流式无总闸」加开关：这是口径修正，不是可选项。
- 不废除逐块读空闲超时：没有它，一条死连接会挂到客户端永不超时为止；它不是总闸。
- 不改 `ttfa_ms` / `ttat` 口径：思考块仍不算「首答」（仅推理的流 TTAT 为空），这与估算口径是两回事。

## 后果

- 上述 62K × 慢推理请求不再被网关在 120s 整掐断；客户端自行决定放弃时机，放弃后走既有 client_closed 清理，日志记 499。
- 失败行不再出现「输出恒为 0」的误导：词元数、吞吐与费用反映已真实转发的生成量；估算口径不变（`usage_estimated=true` 标记保留）。
- 代价：管理侧失去「单个慢流最多占 X 秒」的护栏。慢流会一直占用上游连接与进程内流句柄，直到客户端放手；既有兜底是 `StreamRegistry` 的 SIGTERM 排空（最长 60s）与共享连接池上限（200）。

## 修订（2026-11-16 第二轮）

1. **三道看门狗可按部署覆盖。** 连接/首字节/读空闲超时开放到管理设置页：env 值始终是默认值，覆盖值存 `app_settings` 的 `upstream_timeouts` 行（范围 (0, 86400]，整组保存、可重置回 env），请求路径读取进程内缓存（15 秒 TTL，启动预热；保存/重置即时刷新本进程，其他进程至多一个 TTL 后追上），零 SQL 管线的不变量不受影响。「无总闸」的决策本身不变——覆盖的只是三道「连接死了」看门狗的阈值；`REQUEST_TIMEOUT_S` 与重试预算仍不参与覆盖。
2. **兜底估算的落地实现。** 词元折算优先用 tiktoken `o200k_base`（懒加载，词表不可用时永久退回并记日志）；不可用时按脚本折算公式估算：ASCII（英文/数字/常见符号）按字符数 ÷ 4，非 ASCII（中文/日文等）按字符数 × 1.5（用户指定口径）。缓冲帽：观察器只保留最后 4MB 已转发文本用于编码计数，超帽部分（含思考块）按字符折算保守计入（×1.5/字）。
