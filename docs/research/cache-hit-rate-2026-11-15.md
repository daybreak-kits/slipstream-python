# 缓存命中率归因与优化（2026-11-15）

> 状态：研究记录，只作证据与决策依据，**不是规范正文**。规范看 `docs/ssot.md` §5，决策看 `docs/adr/ADR-068-cache-metrics-and-affinity.md`。

## 0. 结论先行

1. **77% 不是实现缺陷，是「会话内重复前缀没被复用」。** 24h 窗口内 88.77% 的未命中 token **不是新内容**——它们已经出现在同一会话的上一条请求里，却没命中。
2. **用户实测 new-api 的 90%+ 是对的，我们确实更低，但差距不在记账口径上。** 复核（24h，6081 条计入请求）：同会话**没换成员**的轮次 A=78.42%，**换了成员**的轮次 A=64.12%，换成员占全部 token 的 16.0%；同一份库按重复轮次中位数算（cached_b ÷ prompt_b）是 **94.31%**。也就是说「90%+」和「78%」两个数都对，差的是**切片**——面板主指标把冷启动、切成员、厂商侧零命中一起做了 token 加权平均。真实差距按贡献排序：切成员 → 厂商侧零命中 → 每请求换 key（埋雷）。
3. **三个可解释的漏点，按影响排序**：同层跨厂商随机分流（同会话换渠道 → 该会话缓存必然全失）→ 每请求按 request_id 选 API key（一旦某渠道配第二把 key 就会把缓存打散）→ 压缩/重写前缀。**厂商侧 TTL 不是主因**：间隔与命中率没有干净断崖。
4. 已落地：四口径指标、中断流按上游口径入账。**本轮在做**：亲和升级为「跨层钉住上次成功的成员」（§4 第 1 条）。**未验证**：需要真实上游的 A/B 回放（见 §7）。

## 1. 口径必须分开的四个数

| 口径 | 定义 | 24h 实测 | 用途 |
|---|---|---|---|
| A 缓存命中率（主指标） | `cached ÷ (prompt ≥ cached ? prompt : prompt + cached)`，按 token 加权 | **76.98%** | 面板卡片、看趋势 |
| B 请求级命中率 | `cached > 0 的请求数 ÷ 计入请求数` | **93.40%**（5587/5982） | 与 new-api 一类面板对齐时用 |
| C 可缓存占比 | 本请求 prompt 中已在同会话更早请求出现过的 token 占比 | **72.86%**（459,346,044 / 630,411,383，21 会话） | 判断「还能榨出多少」 |
| D 节省 | `Σcached_tokens` 与按模型价格估算的金额 | 485,290,087 token / **$0.00** | 说明缓存省了多少钱 |

D 为 0 不是公式错：该库 17 个渠道模型里只有 1 个配了 input 价且 cache_read 价为空，按规则回落成「按 input 价计 → 无节省」。**面板在 D 为 0 且价格缺失时必须说明原因**，否则会被读成「缓存一点没省」。

A 与 C 的关系是最有用的一对：A 是「实际复用了多少」，C 是「理论上可复用多少」。C 高 A 低 = 没有命中，问题在路由/亲和；C 本身就低 = 前缀在变，问题在请求构造。

## 2. 未命中归因（24h，source=chat，usage_estimated=0，5652 行）

Σprompt 593,548,645 / Σcached 457,616,942 → A = 77.10%（与 §1 的 76.98% 差 0.1pt 是窗口与新增行不同，非口径差）。

未命中 135,931,703 中：

- **88.77%（90,315,161）不是新内容**：这些 token 在同会话上一条请求里已经出现过。
- 真正新增只有 11.23%（11,426,213）。若那 88.77% 全部命中，A 会到 **92.31%**。

零命中请求（366 行 / 37,437,179 prompt token）的归因：

| 原因 | 占比 |
|---|---|
| 同渠道同会话、间隔 <15 分钟，仍整段归零 | **61.58%**（23,052,080） |
| 换渠道或换模型 | 20.24%（7,577,236） |
| 无 session 头 | 15.29% |
| 上下文压缩/收缩 | 1.78% |
| 会话首轮 | 0.69% |
| 间隔 >15 分钟 | 0.43% |

「同渠道同会话、间隔很短却整段归零」占六成，是**最值得查的一类**：它不可能是 TTL，也不可能是换渠道。可能与厂商按块缓存（见下）与「块起点不在上一轮末尾」有关。

渠道构成（24h）：VendorQ 4523 行 76.91%（token 占 81.08%）、minimaxi 1051 行 81.61%（17.69%）、SenseNova 69 行 24.04%（1.23%）、NVIDIA NIM 1 行。**SenseNova 是唯一显著低于均值的渠道**，且其低命中时段伴随 `CIRCUIT_OPEN` 跳过行（不产 token）。

已排除的解释：

- 不是小 prompt 拉低：99.92% 的 token 落在 >32k prompt 上，命中 74–77%。
- 不是估算行污染：`usage_estimated` 行 ≤0.20%。
- 不是重试：20 条最大零命中行里 SenseNova 全是 `status=skipped / error_code=CIRCUIT_OPEN / ms=0`，不产 token；另有一条单次纯 VendorQ 成功、prompt 180,489、cached 0。

### 会话内配对与间隔

同渠道同模型配对的会话内命中率 **78.59%**（3061 对），平均每对新增 24,077 token。`cached_b − prompt_a` 中位数 **−3,848**，92.54% 的配对满足 `cached_b < prompt_a`——即**多数情况下上一轮末尾那截没有被当作前缀复用**。

间隔 → 保留率：<60s 78.48% / 60–300s 81.93% / 600–900s 65.16% / >1800s 58.82%。**没有干净的 TTL 断崖**（若是 5 分钟硬过期，600s 以上应直接掉到 0）。结论：厂商侧过期不是主因，**路由漂移与块边界**才是。

`cached_tokens` 呈块状量化（27648 / 27392 / 7168 / 35072 / 128 / 32000 / 32768 / 24576 / 35584），说明厂商按块命中，且块起点不总在上一轮末尾。

## 3. 厂商前缀缓存机制对照

| 厂商 | 触发 | 最小可缓存前缀 | TTL / 淘汰 | 隔离维度 | 我们的注意点 |
|---|---|---|---|---|---|
| Anthropic | 自动（顶层 `cache_control`）或逐块显式，**最多 4 个断点** | 按模型 512/1024/2048/4096 token | 5 分钟（用一次免费续期）/ 1 小时（写入 2x 价）；读 0.1x | 组织（2026-02-05 起按 workspace） | 前缀顺序 tools → system → messages；**改工具定义会让 tools+system+messages 全失效** |
| OpenAI | 自动 | 1024 token | in_memory 默认 5–10 分钟清；24h 需显式开 | 组织 | **按约前 256 token 的哈希做路由**；`prompt_cache_key` 与之组合提高粘性（官方案例 60%→87%） |
| DeepSeek | 磁盘缓存默认开 | — | — | — | **只有从 token 0 起的完整前缀才算命中**；存储粒度 64 token；usage 报 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` |
| OpenRouter | provider sticky routing | — | 60 分钟不活动失效 | 账号+模型+会话（会话 = 首条 system 与首条非 system 的哈希） | 可用 `session_id` / `x-session-id` 覆盖；**不传会话标识就会漂** |
| NVIDIA NIM | KV cache reuse **默认关** | — | — | — | 需 `NIM_ENABLE_KV_CACHE_REUSE=1` |
| vLLM | `enable_prefix_caching` 需显式开 | — | — | — | 需 `--enable-prompt-tokens-details` 才返回 cached_tokens |
| new-api | **不合成 `cache_control`，只透传** | — | 亲和默认 TTL 3600s 且成功后写回 | 按上游凭据 | 面板口径未确证；用户按 `缓存词元 ÷ 输入词元` 实测得 90%+，**不是**请求级口径（见 §4 复核） |
| LiteLLM | 归一化 cached_tokens；`cache_control_injection_points` 可注入 | — | cache-aware routing 用 rendezvous hashing 把会话钉到 pod | 按上游凭据（文档明说不是按 LiteLLM key） | 它的亲和是**路由级**，不是缓存级 |

## 4. 为什么比 new-api 低（2026-11-15 复核修正）

上一版把 16.4pt 归因成「new-api 是请求级口径」，**这个结论是错的**：用户按 `usage 缓存词元 ÷ 输入词元` 实测 new-api 得到 90%+，与我们同口径。复核后的分解（24h，6081 条计入请求，Σprompt 652,700,665 / Σcached 508,935,770，A=77.97%）：

| 切片 | 行数 | token 占比 | 该切片 A |
|---|---|---|---|
| 全部请求（当前面板主指标） | 6081 | 100% | **77.97%** |
| 其中 r>90% 的行 | 3811 | 64.8% | 96.59% |
| r 在 50%~90% | 1076 | 16.2% | ~78% |
| r 在 0~50% | 812 | 12.9% | ~30% |
| r=0（完全没命中） | 382 | 6.2% | 0% |
| 同会话重复轮次（cached_b ÷ prompt_b） | 4539 对 | — | 中位 **94.31%** |
| 同会话、**成员没换** | 5996 | 83.7% | **78.42%** |
| 同会话、**成员换了** | 733 | 16.0% | **64.12%** |

所以「90%+」和「78%」两个数**都对，只是切片不同**：典型的重复轮次确实在 94% 左右（与用户实测 new-api 的 90%+ 同量级），而面板主指标把冷启动、切成员、厂商侧零命中一起做了 token 加权平均。真正的差距来自下面三件事：

1. **同会话切成员（本轮头号原因，16.0% 的 token）**：同一会话、同一请求模型，上一轮与这一轮落到**不同的渠道成员**时 A 只有 64.12%，没换时是 78.42%；换成员那一档占了全部 token 的 16.0%。原因是厂商侧前缀缓存按「凭据 + 上游模型」隔离——我们曾把「同一渠道」当成同一隔离域，实际 `basis` 的四个成员分属 VendorQ / minimaxi / SenseNova 且各自对应不同上游模型（deepseek-flash / deepseek-v4-flash / MiniMax-M3.1-Flash / sensenova-6.8-flash），换成员 = 换隔离域 = 前缀缓存必然失效。**修复：亲和从「同层内提权」升级为「跨层钉住上次成功的成员」**（ADR-068，本轮实施中）。
2. **厂商侧零命中（6.2% 的 token，本轮只能观测）**：378 次「同会话、同成员、间隔中位数只有几秒、prompt 正常增长（+1,897，与命中轮同量级）」的请求仍然 cached=0，其中 92% 落在 VendorQ。这不是我们的路由问题（也没被请求改写影响：rewrite_applied=1 的 5054 行 A=78.10%，=0 的 993 行 A=78.07%，几乎相同），是厂商侧缓存未命中。
3. **每请求换 key（埋雷，今天没炸）**：`api/src/l05_service/channels.py:191-203` 按 `sha256(request_id)` 取模选 key，即**每个请求都可能换一把 key**。今天 6 个渠道各只有 1 把 key（`len(keys)==1` 直接短路），所以没发生轮换；**一旦给某渠道加第二把 key，该渠道的缓存会立刻被打散**——不同 key 在多数厂商侧属于不同隔离域。

## 5. 优化清单（按性价比排序）

| # | 措施 | 预期收益 | 成本 | 状态 |
|---|---|---|---|---|
| 1 | 面板并排显示 A/B/C/D，附口径与切片说明 | 让「90%+ 与 78% 为何并存」可见 | 小 | 已定（ADR-068） |
| 2 | 会话亲和升级：同会话 TTL 3600s 内**跨层钉住上次成功的成员**（成员不可用才回落层序，失败即清记忆） | 回收 §4「换成员」那一档 16.0% token 的命中率差（64.12% → 78.42% 约合总体 +2.6pt），并阻止后续恶化 | 中 | 本轮实施中 |
| 3 | 同层成员尽量同厂同模 | 同层随机分流不再必然破缓存 | 配置侧 | 用户在调 |
| 4 | 多 key 时把 key 选择从「按 request_id」改为「按会话亲和键」 | 避免加 key 即破缓存 | 小 | **待做** |
| 5 | 请求构造稳定化（system 前缀不抖动、工具定义不随请求变） | 抬高 C 口径，即抬高可缓存上限 | 中 | 待评估 |
| 6 | 对支持显式断点的厂商注入 cache_control（最多 4 点） | 长 system 场景显著 | 中 | 未做 |
| 7 | 压缩策略改为「尾部截断而非重写前缀」 | 避免「压缩即归零」 | 大 | 未做 |

## 6. 不建议做的事

- **不要为了命中率把所有请求钉到单一渠道**：那会把可用性押在一个上游上，与故障转移的设计目标冲突。亲和只在**同层内**生效，正是为此。
- **不要用「请求级命中率」当主指标**：它对短请求权重过高，会把 77% 粉饰成 93%，掩盖真实 token 复用情况。
- **不要相信「加 key 无害」**：见 §4.3。

## 7. 待验证的实验（需要少量上游额度）

- **A/B 回放**：同一批真实会话（按 `x-session-id` 分组）分别走「亲和开 / 关」，比较 A 口径与 TTFT。
- **前缀稳定性对照**：固定一条长 system + 变化 user，验证 C 口径上限。
- **Rust 客户端臂**：用 Rust 客户端打同一个 mock 上游，与 Python 客户端对比，隔离「SDK 开销」与「传输开销」。litellm 的 Rust 网关**不能**替代 Python 侧 chat 路径（`litellm/rust_bridge/catalog.py` 里 `CHAT_COMPLETIONS -> PYTHON_ONLY`），所以只能作客户端臂对照。

## 8. 复现方式

- 只读度量脚本：`cd api && .venv/Scripts/python.exe tests/cache_report.py`（输出 before/after JSON）。
- 口径单测：`tests/test_cache_metrics.py`；亲和单测：`tests/test_session_affinity.py`。
- 库内**没有** `session_id` / `conversation_id` / `prompt_hash` 任何列；会话只能从 `request_headers_json` 的 `x-session-id` 与 `x-bili-plugin-conversation` 取（3824/14774 行带前者，占 7d token 33.89%；10949 行 header 为空对象）。`request_bodies` 表 0 行，**无法在本地重算前缀哈希**——这是 C 口径只能按 `min(prompt, seen)` 估算的原因。
