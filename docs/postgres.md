# PostgreSQL deployment runbook

PostgreSQL replaces the SQLite single writer. It is the precondition for
running more than one gateway process against one database: with SQLite,
several processes that share one file lose log rows silently (measured with
8 writers: rows/req 1.000 -> 0.951, SQLITE_BUSY stayed at 0 the whole time,
so nothing in the logs ever showed the loss).

**Status: the code path is written but was NOT executed against a real
PostgreSQL server in this workspace.** There is no psql, no postgres, no
docker and no network here, so asyncpg could not even be installed. See
"未验证项清单" at the end for the exact list.

### 1.1 行为差异清单 (SQLite vs PostgreSQL)

| topic | SQLite | PostgreSQL | consequence for this app |
|---|---|---|---|
| writers | one writer, the whole file locks | row-level MVCC, many writers | the reason for the migration: no more silent row loss |
| booleans | stored as 0/1 | real BOOLEAN | the data migration converts 0/1 to true/false; the app always writes Python bools |
| floats | REAL | DOUBLE PRECISION | same IEEE value; the generated DDL spells the type out |
| timestamps | BIGINT unix milliseconds | BIGINT unix milliseconds | identical, deliberately not timestamptz |
| JSON payloads | TEXT holding JSON | TEXT holding JSON | the app serialises itself; no json/jsonb column |
| primary keys | TEXT ids generated by the app | TEXT ids generated by the app | no sequences, no SERIAL |
| upserts | ON CONFLICT, SQLite constructor | ON CONFLICT, PostgreSQL constructor | same statement, picked in l04_repo/dialects.py |
| case-insensitive search | lower() emulation | native ILIKE | same result set |
| column introspection | PRAGMA table_info | information_schema.columns | same column set |
| lock contention | database is locked, retried 3x | never retried: the server arbitrates | a PostgreSQL error surfaces instead of being hidden |
| connection pool | small, the single writer bounds it | can grow with the writers | DB_POOL_SIZE / DB_MAX_OVERFLOW |
| durability | WAL + synchronous=NORMAL | server settings (fsync, wal_level) | tune on the server, not in the app |
| schema upgrade | legacy column backfill | ADD COLUMN IF NOT EXISTS only | PostgreSQL needs no SQLite backfills |
| in-process state | per process | still per process | rate limits, quota and the catalog snapshot do not become shared by moving the database |

## 2. Connection string and server setup

    # create the role and the database
    sudo -u postgres psql <<'SQL'
    CREATE ROLE slipstream LOGIN PASSWORD 'change-me';
    CREATE DATABASE slipstream OWNER slipstream ENCODING 'UTF8';
    SQL

    # application
    export DATABASE_URL='postgresql+asyncpg://slipstream:change-me@127.0.0.1:5432/slipstream'

The URL must use the async driver. `postgresql://` and `postgres://` are
rewritten to `postgresql+asyncpg://` automatically; a synchronous driver
(`postgresql+psycopg2://`) is rejected with a message naming the correct
URL. A missing driver raises "PostgreSQL needs the asyncpg driver, which is
not installed: pip install asyncpg==0.30.0" instead of a stack trace.

Pool sizing (per process):

    DB_POOL_SIZE=10            # persistent connections (default)
    DB_MAX_OVERFLOW=20         # burst connections (default)
    DB_POOL_TIMEOUT_S=30
    DB_POOL_RECYCLE_S=1800
    DB_POOL_PRE_PING=true
    DB_STATEMENT_TIMEOUT_MS=0  # PostgreSQL only, 0 = no timeout
    DB_APPLICATION_NAME=slipstream

With PostgreSQL there is no single writer, so the pool may be raised (the
default 10 + 20 overflow is conservative for a gateway process). Keep
`DB_POOL_SIZE` times the number of processes below the server's
`max_connections`: 8 gateway processes at the default 30 connections each
already ask for 240 connections.

## 3. Schema

Two ways to get the schema, both idempotent:

1. The application itself: `init_db()` runs `Base.metadata.create_all` on
   startup, then the PostgreSQL column migration: every column the ORM
   declares but the database is missing is added with `ADD COLUMN IF NOT
   EXISTS`, so a new column in `orm.py` needs no hand-maintained list.
   `POSTGRES_COLUMN_DDL` only overrides the columns that need an explicit
   default; a `NOT NULL` column without one is added nullable, because
   PostgreSQL rejects `ADD COLUMN ... NOT NULL` on a table that already has
   rows and a half-finished startup upgrade is worse than a nullable column
   (backfill it, then `ALTER COLUMN ... SET NOT NULL`). The role needs CREATE
   rights on the target schema.
2. The generated DDL: `db/postgres_schema.sql` (14 tables, 17
   indexes). Regenerate with:

       cd api
       .venv/Scripts/python.exe ../../db/generate_pg_schema.py

The file is derived from `l04_repo/orm.py`, so it cannot drift from what the
application creates.

Column conventions worth knowing before a manual review:

* every id is TEXT generated by the application: no sequences, no
  AUTOINCREMENT, no `last_insert_rowid`,
* every timestamp is a BIGINT of Unix milliseconds (not timestamptz), so the
  values are identical to the SQLite ones,
* JSON payloads are TEXT columns holding a JSON string, not json/jsonb,
* booleans are real BOOLEANs (SQLite stored 0/1).

## 4. Migration order

    # 0. stop the gateway, or keep it on SQLite while you copy
    # 1. create the role and the database (section 2)
    # 2. install the driver in the deployment environment
    pip install asyncpg==0.30.0
    # 3. apply the schema
    psql "$DATABASE_URL" -f db/postgres_schema.sql
    # 4. plan the copy (no connection needed)
    python db/migrate_sqlite_to_postgres.py \
        --sqlite data/app.db \
        --pg-url "$DATABASE_URL" --dry-run
    # 5. copy
    python db/migrate_sqlite_to_postgres.py \
        --sqlite data/app.db \
        --pg-url "$DATABASE_URL" \
        --state data/pg-migrate-state.json
    # 6. verify the row counts
    python db/migrate_sqlite_to_postgres.py \
        --sqlite data/app.db \
        --pg-url "$DATABASE_URL" --verify-only

The copy is idempotent (ON CONFLICT DO NOTHING on the primary key), so step 5
can be repeated. It is resumable: the state file records the last copied
primary key per table, so an interrupted run continues after a restart.
The source file is opened read-only and is never modified.

The plan printed by --dry-run is the checklist for the cutover:

* rows per table: what will be copied,
* missing-in-sqlite: columns the ORM expects but the file does not have. They
  are created empty in PostgreSQL,
* extra-in-sqlite: columns that only exist in the SQLite file. Their data is
  NOT copied, so a non-empty entry needs a decision before the cutover,
* note: tables absent from the sqlite file: tables the ORM knows and the file
  does not have. They start empty,
* warning: tables in the sqlite file that nothing migrates: tables nobody
  owns any more. Their rows stay behind in the SQLite file and are reported
  with their real row count.

Cutover order that avoids losing writes:

1. copy the data while the gateway still writes to SQLite,
2. stop the gateway,
3. run the copy again (only the new rows are missing),
4. switch `DATABASE_URL` to PostgreSQL and start the gateway,
5. keep the SQLite file as a backup until the row counts have been verified.

## 5. Rollback

* Before the cutover: point `DATABASE_URL` back at SQLite. The SQLite file
  was never touched, so this is a configuration change only.
* After the cutover: PostgreSQL keeps receiving writes, so a rollback means
  copying the new rows back into SQLite (the reverse direction is not
  scripted: export with `COPY ... TO CSV` and load with `sqlite3 .import`)
  and then switching the URL back. Losing the minutes between the last
  export and the switch is the price of the rollback.
* The schema migration inside PostgreSQL is additive (ADD COLUMN IF NOT
  EXISTS); it does not drop anything, so an older build can still run
  against the migrated database.

## 6. Pipeline and deployment choices

* `USAGE_PIPELINE=memory` (default in the measurements that produced
  179 RPS per host) keeps the request path free of SQL: the request appends
  to the WAL and a background sink writes the rows. It is orthogonal to the
  database dialect and is still the recommended setting for more than one
  process per host.
* `LITELLM_COST_CALC=off` (the default) must stay off: LiteLLM's own cost
  calculation costs 4-20 ms of CPU per request.
* `CATALOG_POLL_INTERVAL_MS=2000`: in memory mode the request path reads
  an in-process catalog snapshot that is refreshed by a poll (30 s by
  default). A binding created after the process started is invisible until
  the next refresh, and requests in between fail with 404 MODEL_NOT_FOUND.
  2 s shrinks that window to 2 s.
* Multiple processes against one PostgreSQL database are the point of the
  migration: the row loss was caused by the SQLite single writer, not by
  the application. Everything that lives in process memory (rate limiting
  counters, quota, the catalog snapshot) is still per process, so either run
  one process per host or move that state out.
* Keep `UPSTREAM_TRANSPORT=litellm` (the default) when switching to
  PostgreSQL: the dialect change does not depend on the upstream transport.
  The transport verdict belongs to docs/upstream_transport.md, and its
  first numbers (16 concurrent clients) favour `httpx` (30.80 vs 20.72 rps
  non-stream, 21.96 vs 12.95 rps short-stream), while the long-stream cells
  are still being re-measured. Until that verdict lands, `httpx` stays an
  escape hatch (`UPSTREAM_TRANSPORT=httpx`), not the default.

### 7.1 本地已验证 (verified in this workspace)

* 43 dialect unit tests pass without any server (api/tests/test_postgres_dialect.py,
  43 passed in 5.63 s): URL normalisation, the driver check, ON CONFLICT
  compiled for both dialects, the SQLite-only lock retry, per-dialect column
  introspection, the generated schema against every ORM table, the column
  upgrade covering every ORM column, and the migration planning, batching,
  conversion and state handling.

  NORMAL, busy_timeout and foreign_keys (asserted in the same test file).
* The three write statements render to the intended PostgreSQL SQL (rendered
  with the postgresql dialect, no server involved): request_logs ends in
  ON CONFLICT DO NOTHING (no target, so a duplicate primary key or request_id
  is absorbed), request_ledger in ON CONFLICT (request_id) DO NOTHING, and
  request_bodies in ON CONFLICT (request_id) DO UPDATE SET ....

  (the 8 skips are the PostgreSQL integration tests, which need
  LLMAPI_TEST_PG_DSN).
* Regression subset -k db or schema or repo or log or usage or pipeline:
  134 passed, 3 skipped, 488 deselected in 687.72 s, exit 0.
* Real data dry run on a read-only copy of the live database
  (api/data/app.db, 29 MB): 14 tables planned, 11 387 rows in total,
  request_logs 11 321 rows, request_bodies / request_ledger / ledger_adjustments /
  daily_aggregates 0 rows, no missing-in-sqlite column, no extra-in-sqlite

### 7.2 未验证项清单 (not verified here)

Everything below is written but was never executed against a real
PostgreSQL server in this workspace (no postgres, no psql, no docker, no
network, asyncpg not installable):

1. `build_engine("postgresql+asyncpg://...")` creating the engine and the
   pool with `server_settings` / `statement_timeout`.
2. `init_db()` on PostgreSQL: create_all plus the idempotent
   ADD COLUMN IF NOT EXISTS migration.
3. `ON CONFLICT DO NOTHING` on `request_logs` (no conflict target) and on
   `request_ledger` (target `request_id`).
4. The `request_bodies` upsert (`ON CONFLICT (request_id) DO UPDATE`).
5. Boolean, BIGINT-millisecond and TEXT-JSON round trips.
6. `information_schema` column introspection.
7. The data migration script's PostgreSQL round trip (batching, ON CONFLICT,
   resume, verification). Only the planning, batching, conversion and state
   handling were unit tested.
8. Concurrency: several processes writing the same table at once, which is
   the whole reason for the migration.
9. The `postgres_schema.sql` file was rendered from the ORM metadata but
   never applied to a server; run it once and compare with what the
   application creates.

Run the integration tests against a real server to close items 1-8:
